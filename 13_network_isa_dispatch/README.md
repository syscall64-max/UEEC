# UEEC — ქსელში არქიტექტურით, OS-ითა და ტექნოლოგიით ნოდის არჩევა

`12_shared_metadata` მაგალითის გაგრძელება: სერვერს აქვს 12 არქიტექტურის
29 ნოდის შემცველი UEEC, კლიენტი კი იღებს **მხოლოდ ერთ თავსებად ნოდს**.
კლიენტი მიღებული მონაცემებით ქმნის ერთნოდიან UEEC ფაილს კომპაქტურ ან
გრანულირებულ განლაგებაში. ქსელური პროგრამა მიღებულ კოდს ავტომატურად არ უშვებს.

კლიენტი თავად ადგენს:

- პროცესორის არქიტექტურას;
- ოპერაციულ სისტემას — ამ განხორციელებაში Linux;
- კოდის ბაიტების რიგს;
- CPU-სა და OS-ში შესრულებისთვის ხელმისაწვდომ ISA ტექნოლოგიებს.

მაგალითად, x86-64-ზე AVX/AVX-512-ის ფიზიკური მხარდაჭერა საკმარისი არ არის:
კლიენტი CPUID-სთან ერთად XSAVE/OSXSAVE/XGETBV-საც ამოწმებს. სხვა ოჯახებისთვის
გამოიყენება იგივე auxv/prctl/hwprobe მექანიზმები, რაც წინა ჩამტვირთავში.
სერვერი **კლიენტის**, და არა საკუთარი პროცესორის შესაძლებლობებით არჩევს ნოდს.

ეს არის Linux-ის leaf-ფუნქციის (`sum`) დემონსტრაცია. OS-ის ფილტრი უკვე მოქმედებს,
მაგრამ Windows/macOS კლიენტი ან ჩამტვირთავი ამით არ დამატებულა. DATA/RELOC/IMPORT
სექციების მქონე ზოგადი პროგრამის ქსელური ამოღება ამ მაგალითის ფარგლებს გარეთაა.

## დამოკიდებულებები და სწრაფი შემოწმება

Debian/Ubuntu-ზე საჭიროა GCC, binutils, make, Python 3.10+, OpenSSL და მისი C ჰედერები:

```sh
sudo apt install build-essential python3 openssl libssl-dev
cd 13_network_isa_dispatch
make test
```

`make test` თვითონ ქმნის დროებით სერტიფიკატს, იწყებს ადგილობრივ TLS სერვერს,
ატარებს მიმდინარე არქიტექტურის ტესტებს და სერვერს აჩერებს. მეორე ტერმინალი საჭირო არ არის.
ტესტის დროებითი პირადი გასაღები გამოშვების არქივში არ შედის.

მხოლოდ ქსელური ტესტი: `make test-network`.
მხოლოდ აგება: `make all`.

## ხელით გაშვება

პირველ ტერმინალში:

```sh
make all
make cert
make serve
```

მეორე ტერმინალში, იმავე საქაღალდიდან:

```sh
# ავტომატური CPU/OS/ISA გამოკითხვა; საუკეთესო თავსებადი ნოდის მიღება
./build/ueec-net client --ca build/cert.pem --output build/received.ueec

# მიღებული ფაილის დათვალიერება და ცალკე გაშვება
./build/ueec-loader --list-technologies build/received.ueec
./build/ueec-loader build/received.ueec

# კონკრეტული ტექნოლოგია; მიუწვდომლობისას შეცდომა
./build/ueec-net client --ca build/cert.pem --technology avx2 --output build/avx2.ueec

# მოთხოვნის მიუწვდომლობისას ავტომატური არჩევა
./build/ueec-net client --ca build/cert.pem --technology avx512f --fallback --output build/fallback.ueec

# იგივე შერჩეული ნოდი, ლოკალურად 4096-ბაიტიანი გრანულებით
./build/ueec-net client --ca build/cert.pem --mode granulated --granule 4096 --output build/granulated.ueec
```

გამოსატანი ფაილი წინასწარ არ უნდა არსებობდეს: კლიენტი მას არ გადაწერს.
`--technology`-ის გარეშე არჩევა ავტომატურია. თავსებად ნოდებს შორის აირჩევა
ყველაზე მაღალი ავტორის მიერ მინიჭებული პრიორიტეტი; ეს სიჩქარის გაზომვა არ არის.
ზუსტი პროფილები (`avx2`, `sse2`, `neon` და სხვ.) სხვა პროფილით ჩუმად არ იცვლება.
სხვა მხარდაჭერილი ჯგუფის, მაგალითად `avx`-ის, მოთხოვნა ნიშნავს ამ ბიტის შემცველ პროფილს.
თანაბარი პრიორიტეტებისას პირველი თავსებადი ნოდი იმარჯვებს.

სხვა არქიტექტურებზე შესაბამისი ტექნოლოგიებია `neon`, `sve`, `lsx`, `lasx`,
`altivec`, `rvv`, `vis`, `vx`; `scalar` ნიშნავს დამატებითი ISA-ს გარეშე ვარიანტს.
OS/არქიტექტურის შესაბამისი ნოდის არყოფნისას ფაილი არ შეიქმნება.

## სხვა კომპიუტერიდან დაკავშირება

სერვერს აქვს `--bind ADDRESS`, კლიენტს — `--host HOST`. ნაგულისხმევია მხოლოდ
loopback: სერვერი `127.0.0.1:9443`, კლიენტი `localhost:9443`.

```sh
./build/ueec-net server --bind 0.0.0.0 --port 9443 --source build/sum.ueec --cert server.pem --key server.key
./build/ueec-net client --host server.example --port 9443 --ca trusted-ca.pem --output result.ueec
```

სერტიფიკატის SAN უნდა შეესაბამებოდეს რეალურ DNS სახელს ან IP მისამართს.
`make cert` ქმნის მხოლოდ localhost/127.0.0.1/::1-ის სატესტო სერტიფიკატს.
სერტიფიკატისა და სახელის შემოწმების გამორთვის რეჟიმი არ არის.
კლიენტის არქიტექტურის შესახებ მონაცემები მოთხოვნაა და არა მოწყობილობის ატესტაცია.
ჩამოტვირთვა ავტომატურ შესრულებას არ ნიშნავს.

სერვერი მოთხოვნებს თანმიმდევრულად ამუშავებს. კავშირის წაკითხვის/ჩაწერის timeout
არის 30 წამი; თვითონ listening socket-ს ეს timeout არ აქვს, ამიტომ უმოქმედო
სერვერი 30 წამში აღარ სრულდება. ეს სატესტო სერვერია, არა მასშტაბური ჰოსტინგის სერვისი.

## რა იგზავნება და როგორ გადაიწერება მეტამონაცემები

საწყისი ფაილი: 29 ნოდი, 29 CODE და ერთი საერთო METADATA, 5719 ბაიტი.
საერთო MD-ის ჩანაწერში `node_index` ყოველთვის `uint16_t`-ია.
count/offset-ის სიგანე შეიძლება იყოს 16/32/64 ბიტი; ორივე endian და ძველი
per-node design=0 წყარო სერვერის მიერ იკითხება.

არჩევის შემდეგ სერვერი თავიდან აწყობს ფაილს:

| ნაწილი | მიღებულ ფაილში |
| --- | --- |
| ნოდების რაოდენობა | 1 |
| ნოდის ინდექსი | 0 |
| HEADER | ახალი, მხოლოდ ერთი ნოდის აღწერით |
| CODE | მხოლოდ არჩეული ნოდის კოდი, ბაიტები უცვლელია |
| METADATA | მხოლოდ არჩეული ნოდის REQUIRED და PRIORITY |
| მეტამონაცემების node_index | ორივე ჩანაწერში 0 |
| კოდის endian | არჩეული ნოდის თავდაპირველი endian |
| ფაილის გარე სტრუქტურა და MD | კანონიკური little-endian, SH16 / MD16, design=1 |

სხვა ნოდების CODE და საერთო MD-ის სხვა ჩანაწერები არ გადაიცემა.
ქსელში იგზავნება კომპაქტური ერთნოდიანი UEEC. კლიენტი ამოწმებს TLS-ს,
SHA-256-ს, ფორმატს, ნოდის რაოდენობას, არქიტექტურას, OS-ს, endian-ს, მოთხოვნებსა
და პრიორიტეტს; შემდეგ თავიდან აწყობს არჩეულ ლოკალურ განლაგებას.

გრანულირებულ რეჟიმში თითოეული სამი სექცია — HEADER, CODE, METADATA — ცალკე
მრგვალდება. 4096-ბაიტიანი გრანულისა და ამ მცირე CODE-ების შემთხვევაში გამოდის
12288 ბაიტი. ქსელში padding არ იგზავნება.
ჩამტვირთავი METADATA-ს არჩევისთვის იყენებს და შესრულებამდე მის mapping-ს ხსნის.

ბინარული პროტოკოლი აღწერილია [PROTOCOL.md](PROTOCOL.md)-ში. პროტოკოლი `UEC2`
შეგნებულად განსხვავდება ეტაპი 10-ის `UEC1`-ისგან: მისი ძველი კლიენტი ამ სერვერის
კლიენტად არ ითვლება.

## 12 არქიტექტურის სრული შემოწმება

საჭიროა წინა მაგალითების სრული cross-კომპილატორები და QEMU:

```sh
set -o pipefail
make test-all 2>&1 | tee network-isa-test.log
printf 'Exit code: %s\n' "$?"
```

ტესტები თვითონ იწყებენ/აჩერებენ სერვერებს; წინასწარ `make serve` არ გაუშვა.
პირველად სრულდება 12 არქიტექტურის არსებული dispatch/format ტესტები, შემდეგ
12 არქიტექტურის ქსელური ტესტები და ბოლოს native ქსელური ტესტი.
სამიზნის გამოტოვება PASS-ად არ ითვლება.

Cross OpenSSL საჭირო არ არის: ყოველი სამიზნისთვის C-ზე აგებულია
`ueec-request-ARCH`, რომელიც QEMU-ში თვითონ ადგენს CPU/OS/ISA-ს და ქმნის
64-ბაიტიან მოთხოვნას. ადგილობრივი OpenSSL კლიენტი ამ მოთხოვნას უცვლელად
გზავნის; მიღებული UEEC იმავე სამიზნის ჩამტვირთავით სრულდება QEMU-ში.
ლოგში გამიჯნულია `profile=QEMU` და `transport=native-TLS`.
ეს არ არის უცხო არქიტექტურის TLS ბიბლიოთეკის შესრულების მტკიცება.
რეალურ სხვა Linux მოწყობილობაზე ქსელური კლიენტის აგებას იმ მოწყობილობის
ჩვეულებრივი native OpenSSL ჰედერები და ბიბლიოთეკები სჭირდება.

```sh
# ერთი სამიზნე
make loader ARCH=powerpc64
make network generate
python3 test_network.py --arch powerpc64 --qemu

# მხოლოდ გადაცემა/ფაილის სტრუქტურა: 29 ვარიანტი × 2 რეჟიმი
make test-transfer-all
```

`test-transfer-all` იყენებს **სინთეზურ** მოთხოვნებს. იგი ამოწმებს 12 არქიტექტურის
ყველა 29 კოდის ზუსტად გადაცემას, მაგრამ არც CPU-ს აღმოჩენას და არც სამიზნე
კოდის შესრულებას არ ამტკიცებს. ამისთვის არსებობს სრული `test-all`.

ხელით სატესტო პროფილის შექმნა და გადაცემა:

```sh
./build/ueec-request --limit-isa scalar --output build/scalar.request
./build/ueec-net client --ca build/cert.pem --request-file build/scalar.request --output build/scalar.ueec
```

`--limit-isa` მხოლოდ შესაძლებლობებს შლის; ვერ ამატებს. `--request-file` გამოიყენება
პროფილის გადასატანად და უცხო კოდის ავტომატურ გაშვებას არ იწვევს.
იგი კლიენტის `--technology`, `--fallback` ან `--limit-isa` პარამეტრებს არ ერევა:
ეს პარამეტრები საჭიროებისას მოთხოვნის გენერატორს გადაეცემა.

აგების `CC_ARCH` ცვლადები შენარჩუნებულია. RISC-V32-ზე ავტომატურად მოწმდება
`/opt/riscv32/bin/riscv32-unknown-linux-gnu-gcc`.
PowerPC64-ის ძირითადი პროფილი ისევ POWER8-ია; POWER5+ დადასტურებული არ არის.
