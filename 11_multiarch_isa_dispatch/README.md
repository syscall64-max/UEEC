## PowerPC64: GCC 15-ის შესწორება

GCC 15.3-ით გამეორდა ორივე ნოდის პირველი გამოძახებისას SIGSEGV. კომპილატორი
შლიდა დროებითი ELFv1 დესკრიპტორის შევსებას: ABI-ის მიერ ფუნქციის მაჩვენებლით
შესრულებული წაკითხვები C-ის dead-store ანალიზისთვის ხილული არ იყო.
`loader.c`-ში დამატებული ცარიელი GNU asm, descriptor-ის memory operand-ით
და memory clobber-ით, ამ ჩაწერას ინარჩუნებს. შესრულებად კოდს იგი არ ამატებს.

შესწორება შემოწმდა GCC 15.3-ის `-O0`, `-O2`, `-O3`, `-Os` რეჟიმებში და
`-O2 -flto`-თი. scalar და AltiVec ორივე გადის შესრულების ტესტებს.
ძველი ვერსიისათვის დართულია `fix-powerpc64-gcc15.patch`; ეს არქივი უკვე
შესწორებულია. მომხმარებლის GCC 15.2/QEMU 10.2.1 გარემოში ხელახლა გაშვება
საჭიროა — აქ გამეორება და შემოწმება გაკეთდა GCC 15.3/QEMU 10.0.13-ით.

## QEMU CPU პროფილი და libc-ის მოთხოვნები

**PowerPC64-ის სავალდებულო ტესტის პროფილია POWER8.** POWER5+ ამ მაგალითის
ავტომატური ტესტებიდან გამორიცხულია, მცირე ABI probe-ის შედეგის მიუხედავად.
POWER8-ზე სრულდება scalar და AltiVec, ხოლო არჩევა, მოთხოვნის უარყოფა და
`--fallback` საერთო ტესტებში მოწმდება. PowerPC64-ის ტესტი 33 შემოწმებას შეიცავს.
ეს ძველ POWER5+ პროცესორზე მხარდაჭერის დადასტურებას არ ნიშნავს.

Ubuntu 25.10/26.04-ის RISC-V ბიბლიოთეკების ბაზაა RVA23. მხოლოდ
`rv64,v=true` ამ პროფილის ყველა გაფართოებას არ რთავს. RISC-V64-ის მთავარი
ტესტი ახლა იყენებს `max,vlen=128,elen=64`-ს; `--cpu`-ით სხვა პროფილის
მითითებაც შეიძლება. ეს ცვლილება CODE-ის მოთხოვნებს არ ცვლის.

ყოველი ჩამტვირთავის გვერდით იმავე compiler/libc-ით აგებულია მცირე
`abi-probe-ARCH` C პროგრამა (`abi_probe.c`). მას UEEC კოდი არ აქვს.
დამატებითი ძველი CPU მოდელის ან გამორთული ტექნოლოგიის ტესტამდე ჯერ ეს
პროგრამა მოწმდება. თუ probe ამ CPU-ზე ვერ მუშაობს, შეუძლებელია იმავე
libc-ით დაკავშირებული ჩამტვირთავის გაშვების უნივერსალურად მოთხოვნაც.

ასეთ შემთხვევაში მოდელზე შემოწმება აღინიშნება როგორც მიუწვდომელი,
stdout-ში იბეჭდება მიზეზი და JSON-ში ინახება `abi_preflight` შედეგი.
საერთო სამი უარყოფითი dispatch შემთხვევა მაინც სრულდება ძირითად CPU-ზე
`--limit-isa scalar`-ით: ავტომატური scalar არჩევა, ვექტორული მოთხოვნის
უარყოფა და `--fallback`-ით scalar-ზე გადასვლა. ეს შესაძლებლობების ნიღბის
შეზღუდვაა და ძველი CPU მოდელის მხარდაჭერად არ ითვლება.

თუ probe წარმატებულია, სამივე დამატებითი CPU-model ტესტის წარმატებაც
სავალდებულოა. UEEC კოდის ავარია ამ მექანიზმით არ იმალება. არასწორი CPU
პარამეტრები, დაკარგული probe და სხვა აგების შეცდომები ტესტს წყვეტს.

შედეგში `negative=capability-mask` და `negative=cpu-model+capability-mask`
ერთმანეთისგან განსხვავდება. შემოწმებების რაოდენობა libc-ის ბაზაზეა
დამოკიდებული; ყველა 12 არქიტექტურის CODE და შესაბამისი ნოდების არჩევა
ყველა შემთხვევაში მოწმდება. POWER5+ ამ წინასწარი შემოწმებითაც აღარ
ბრუნდება სავალდებულო ტესტებში: მცირე პროგრამის წარმატება სრული ჩამტვირთავის
ყველა გზის თავსებადობის გარანტია არ არის.

[Ubuntu-ს არქიტექტურების ბაზები](https://ubuntu.com/project/docs/how-ubuntu-is-made/concepts/supported-architectures/)
და [26.04-ის მოთხოვნები](https://documentation.ubuntu.com/release-notes/26.04/summary-for-lts-users/).

## დაწყება

არქივის გახსნის შემდეგ x86-64 Linux კომპიუტერზე:

```sh
cd 11_multiarch_isa_dispatch
make test
```

პირველი გაშვებისთვის საჭიროა GCC, binutils, make და Python 3.10 ან უფრო ახალი.
ნამდვილი მანქანური CODE უკვე დართულია `payloads/`-ში SHA-256 მანიფესტებით.
ამიტომ `make test` სხვა არქიტექტურების კომპილატორებს არ ითხოვს: აგებს მიმდინარე
კომპიუტერის ჩამტვირთავს, ქმნის უნივერსალურ ფაილს და ატარებს შესაბამის ტესტებს.

```sh
# ავტომატური არჩევა
./build/ueec-loader build/sum.ueec

# პროცესორისათვის ხელმისაწვდომი ჯგუფები
./build/ueec-loader --groups

# ფაილში ყველა არქიტექტურისა და ტექნოლოგიის ნახვა
./build/ueec-loader --list-technologies build/sum.ueec

# მხოლოდ მიმდინარე არქიტექტურის ვარიანტები
./build/ueec-loader --list-technologies --host-only build/sum.ueec

# ტექნოლოგიის პირდაპირი არჩევა
./build/ueec-loader --technology avx2 build/sum.ueec

# მოთხოვნილი ტექნოლოგიის მიუწვდომლობისას ავტომატური არჩევა
./build/ueec-loader --technology avx512f --fallback build/sum.ueec

# არჩევის ჩვენება CODE-ის შესრულების გარეშე
./build/ueec-loader --no-run build/sum.ueec
```

Intel i5-10400-ზე x86-64 ვარიანტებიდან ავტომატური არჩევანი უნდა იყოს AVX2.
`--technology avx512f` მხარდაჭერის გარეშე შეცდომით სრულდება; `--fallback`-ით
ავტომატური არჩევანი კვლავ AVX2 იქნება. ARM64 ჩამტვირთავთან მოთხოვნის მაგალითია
`--technology sve`, RISC-V-სთან — `--technology rvv`.

## არჩევის წესი

1. ფილტრი ამოწმებს UEEC machine-ს, Linux გარემოს, CODE-ის ბაიტების რიგს და
   ამ მაგალითის user/library რეჟიმს.
2. ნოდის METADATA-დან იკითხება არქიტექტურის მოთხოვნების `uint64_t` ნიღაბი.
3. ნოდი თავსებადია, თუ **ყველა** მოთხოვნილი ბიტი შესრულებისთვის ხელმისაწვდომია:
   `(required & ~usable) == 0`.
4. ავტომატური არჩევანი იღებს თავსებად ნოდს ყველაზე დიდი `priority` მნიშვნელობით.
5. `--technology NAME` ითხოვს შესაბამის ტექნოლოგიას. მიუწვდომელი ან ფაილში
   არარსებული ტექნოლოგია შეცდომაა, თუ `--fallback` არ არის მითითებული.

scalar-ის პრიორიტეტია 100, პირველი ვექტორული ვარიანტის — 200, შემდეგის — 300,
AVX-512F-ის — 400. თანაბარი პრიორიტეტებისას პირველი შესაბამისი ნოდი აირჩევა.
ეს **ავტორის მიერ განსაზღვრული უპირატესობაა**. პროგრამა სიჩქარეს არ ზომავს და
მაღალი პრიორიტეტი ყველა პროცესორზე უკეთეს წარმადობას არ ამტკიცებს.

`--technology neon` ირჩევს NEON ვარიანტს, მაშინაც კი, როცა SVE-ც ხელმისაწვდომია.
`--limit-isa scalar` ტესტისთვის შლის დამატებითი ბრძანებების მხარდაჭერას;
იგი CPU-ს შესაძლებლობებს ვერ ამატებს და ემულატორს არ წარმოადგენს.

## როგორ განისაზღვრება მხარდაჭერა

| ოჯახი | შემოწმება |
| --- | --- |
| x86, x86-64 | CPUID; AVX/AVX-512-სთვის XSAVE, OSXSAVE და XGETBV; AMX ამ მაგალითში არ ირთვება |
| ARM32, ARM64 | Linux AT_HWCAP / AT_HWCAP2; SVE-სთვის დამატებით PR_SVE_GET_VL |
| LoongArch, PowerPC, SPARC, S390X | Linux AT_HWCAP / AT_HWCAP2 |
| RISC-V | auxv; Zba/Zbb/Zbs-ისთვის riscv_hwprobe; RVV-სთვის დამატებით მიმდინარე ნაკადის V_GET_CONTROL |

QEMU 10.0.13 RISC-V-ზე V-ს auxv-ში აცხადებს, მაგრამ V_GET_CONTROL-ს არ ასრულებს.
ამ შემთხვევისთვის ჩამტვირთავი მემკვიდრეობით მიღებული პოლიტიკის მქონე შვილობილ
პროცესში ამოწმებს `vsetvli`-ს. მხოლოდ წარმატების შემდეგ ითვლება RVV გამოსაყენებლად.
თუ კონტროლის ინტერფეისი პირდაპირ ამბობს OFF-ს, RVV არ აირჩევა; პოლიტიკა არ იცვლება.

არაქს86 არქიტექტურებზე `--groups`-ის `hardware` სვეტში წერია `n/a`:
auxv გვაძლევს OS-ის მიერ გამოცხადებულ ხელმისაწვდომობას და არა ცალკე ფიზიკურ
პროცესორზე ჩატარებული გამოკითხვის შედეგს. QEMU-ში ეს მონაცემებიც ემულირებულ
პროცესორს ეკუთვნის.

სრული ISA კატალოგები აქ არ არის შეტანილი. `--groups` აჩვენებს ამ მაგალითში
განსაზღვრულ ჯგუფებს, ხოლო შემსრულებელი CODE ვარიანტები ზემოთ მოყვანილ ცხრილშია.

## C სტრუქტურები და METADATA

`ueec_metadata.h` განსაზღვრავს x86/x86-64-ის საერთო 49 ბიტს.
`ueec_capabilities.h` ამატებს ARM32, ARM64, LoongArch, PowerPC, RISC-V,
SPARC და S390X ოჯახების რვაბაიტიან სტრუქტურებს. PowerPC32/64, RISC-V32/64
და SPARC32/64 შესაბამისი ოჯახის ბიტების ერთსა და იმავე სივრცეს იყენებენ.

C bitfield-ების მეხსიერების განლაგება კომპილატორისა და ABI-ის მიხედვით იცვლება.
ფაილში მათი პირდაპირი `fwrite`/`memcpy` არ გამოიყენება. მოთხოვნები ჩაიწერება
გამოკვეთილი `uint64_t` ნიღბით და ფაილში გამოცხადებული ბაიტების რიგით.

METADATA-ს ინდექსირებული დიზაინი:

```c
/* ცალკეული მნიშვნელობები ფაილის endian-ით იკითხება. */
uint16_t format;             /* 0:16, 1:32, 2:64-ბიტიანი count/offset */
uint16_t design;             /* 0: indexed */
/* count; elements[count+1]; data; ბოლო element არის sentinel */
```

| ელემენტის ტიპი | მნიშვნელობა |
| --- | --- |
| 0 | END sentinel |
| 1 | x86 / x86-64 REQUIRED, uint64 |
| 2 | PRIORITY, uint16 |
| 0x100 | ARM32 REQUIRED, uint64 |
| 0x101 | ARM64 REQUIRED, uint64 |
| 0x102 | LoongArch REQUIRED, uint64 |
| 0x103 | PowerPC REQUIRED, uint64 |
| 0x105 | RISC-V REQUIRED, uint64 |
| 0x107 | SPARC REQUIRED, uint64 |
| 0x10b | S390X REQUIRED, uint64 |

ეს ნომრები მაგალითის **საცდელი ინდექსებია**, არა UEEC-ის ძირითადი რეგისტრის
დასრულებული ცვლილება. METADATA სექციის ტიპია 13; HEADER-ის არსებული სტრუქტურა
უცვლელია. REQUIRED სავალდებულოა; PRIORITY-ის არყოფნისას მნიშვნელობა 0-ია.
უცნობი/განმეორებული ელემენტები და დაზიანებული ინდექსები უარყოფილია.
უცნობი მოთხოვნის ბიტი შეუთავსებლობას ნიშნავს.

კონტეინერის endian დამოუკიდებელია CODE-ის endian-ისგან. PowerPC, SPARC და
S390X ნოდებს `encode=1` აქვთ; დანარჩენებს — 0. გენერატორი მხარს უჭერს როგორც
LE, ისე BE კონტეინერს და METADATA-ს სამივე სიგანეს.

## ყველა არქიტექტურის ტესტი

თქვენს გარემოში, სადაც წინა მაგალითების 12 კომპილატორი და QEMU უკვე გაქვთ:

```sh
set -o pipefail
make test-all 2>&1 | tee isa-dispatch-test.log
echo "დასრულების კოდი: $?"
```

ტესტი აგებს 12 ჩამტვირთავს, უშვებს ყველა სამიზნეს QEMU-ში და ბოლოს მიმდინარე
არქიტექტურის ჩამტვირთავს უშუალოდაც ამოწმებს. გამოტოვებული სამიზნე PASS-ად
არ ითვლება: კომპილატორის ან QEMU-ს არქონა ტესტს წყვეტს.

ნაგულისხმევი კომპილატორების სია `architectures.py`-შია. RISC-V32-ზე ავტომატურად
მოიძებნება თქვენი `/opt/riscv32/bin/riscv32-unknown-linux-gnu-gcc`.
სხვა მდებარეობისთვის:

```sh
CC_RISCV32=/სრული/გზა/riscv32-unknown-linux-gnu-gcc make test-all
```

დამატებით შესაცვლელი ცვლადებია `CC_ARM32`, `CC_ARM64`, `CC_LOONGARCH64`,
`CC_POWERPC32`, `CC_POWERPC64`, `CC_RISCV64`, `CC_SPARC32`, `CC_SPARC64`,
`CC_X86`, `CC_X86_64`, `CC_S390X`. Python-ის აგების სკრიპტი გარემოდან კითხულობს
მათ. native აგებისთვის ჩვეულებრივი `CC`-ც მუშაობს.

მაგალითად, QEMU-ში ცალკე გაშვება:

```sh
qemu-aarch64 -cpu max ./build/ueec-loader-arm64 --technology sve build/sum.ueec
qemu-loongarch64 -cpu max ./build/ueec-loader-loongarch64 --technology lasx build/sum.ueec
qemu-riscv32 -cpu rv32,v=true,vlen=128,elen=64 ./build/ueec-loader-riscv32 --technology rvv build/sum.ueec
qemu-ppc64 -cpu power8 ./build/ueec-loader-powerpc64 --technology altivec build/sum.ueec
```

QEMU-ში ფუნქციის წარმატებული შესრულება დადასტურებულია. არაქს86 ფიზიკურ
მოწყობილობებზე ეს ახალი მაგალითი აქ არ შემოწმებულა. წინა MPU/MCU მაგალითების
რეალურ მოწყობილობებზე მუშაობა ამ ახალი მაგალითის შემოწმებისგან დამოუკიდებელია.

## CODE-ის თავიდან აგება

ყველა cross-კომპილატორის არსებობისას:

```sh
make payloads
make test-all
```

მხოლოდ მიმდინარე არქიტექტურის CODE-ისთვის:

```sh
make payloads-native
make test
```

`sum.c` ვექტორული ვარიანტების საერთო წყაროა; RVV/SVE ინტრინსიკებით იწერება,
VIS იყენებს `fpadd32` built-in-ს, ფიქსირებული ვექტორები — GCC-ის vector ტიპებს.
x86-64 იყენებს `sum_x86_64.S` რეალიზაციებს.
`tools/build.py` იყენებს შესაბამის binutils-ს, ამოწმებს საწყის მისამართს 0,
დამოუკიდებელი DATA/კონსტანტების არქონას და მოსალოდნელ ISA ინსტრუქციას.
დისასემბლირებული შედეგები ინახება `build/objects/`-ში.

მოწოდებული ნედლი CODE GNU ინსტრუმენტებით აიგო: Debian GCC 14.2; RISC-V32 —
Bootlin GCC 15.3 / musl. კომპილატორი არქივში არ შედის. RVV-ის თავიდან აგებისთვის
საჭიროა ვექტორული ინტრინსიკების მხარდამჭერი GCC; ამ მაგალითისთვის შემოწმდა GCC 14+.

scalar აქ ნიშნავს ამავე Linux ABI-ის ფარგლებში ვექტორული დაჩქარების გარეშე
რეალიზაციას. იგი არ ნიშნავს ყველა ისტორიულ მოდელთან თავსებადობას: ARM32-ის
აგების ბაზაა ARMv7 hard-float, S390X-ის — z196, SPARC32-ის გარემოა v8plus.
ჩამტვირთავის სტატიკურ libc-ს თავისი მინიმალური მოთხოვნებიც აქვს. ამიტომ SPARC-ზე
VIS-ის გარეშე QEMU მოდელით Debian libc-ის დაწყება ამ ტესტში არ მოწმდება;
scalar არჩევა იქ მოწმდება `--limit-isa scalar`-ით. LoongArch-ზე უარყოფითი მოდელის
ტესტი შლის LASX-ს და ტოვებს LSX-ს.

## შესრულების გზა და შემოწმება

ჩამტვირთავი მთელ ფაილს მხოლოდ წაკითხვისთვის ასახავს, ამოწმებს ინდექსებს,
ირჩევს ნოდს და კოპირებს მხოლოდ მის CODE-ს RW მეხსიერებაში. ინსტრუქციების
ქეშის გასუფთავების შემდეგ დაცვა იცვლება RX-ზე. ფაილის საერთო ასახვა და fd
თავისუფლდება ფუნქციის გამოძახებამდე. RWX მეხსიერება არ გამოიყენება.
PowerPC64 ELFv1-სთვის იქმნება ფუნქციის დროებითი დესკრიპტორი; ნედლი ფუნქცია
არ იყენებს TOC-ს და გლობალურ მონაცემებს.

თითოეული გაშვებული CODE გადის 256 სიგრძის/გასწორების კომბინაციას,
32 guard-page შემთხვევას, NULL/ნულოვანი სიგრძის და გადავსების შემოწმებას.
კონტეინერის ტესტები მოიცავს პრიორიტეტისა და ნოდების რიგის დამოუკიდებლობას,
სხვადასხვა endian/სიგანეს, უცნობ მოთხოვნებს, დაზიანებულ METADATA-სა და
სხვა არქიტექტურის ნოდის შესრულების უარყოფას.

ჩამტვირთავი ამ მაგალითში უშვებს კონკრეტულ leaf ფუნქციას ცნობადი ABI-ით;
ზოგადი პროგრამის ყველა სექციის, იმპორტის ან რელოკაციის ჩატვირთვის ახალი
რეალიზაცია აქ არ არის დამატებული. წინა `00`–`10` ეტაპების ფაილები არ იცვლება.

დეტალური შედეგები: `VALIDATION.md`, `validation/results/` და `validation/test-all.log`.
