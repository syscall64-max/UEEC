# UEEC — საერთო მეტამონაცემების სექცია

ეს დამოუკიდებლად ასაგები მაგალითი აჩვენებს CPU შესაძლებლობების მეტამონაცემებს
და მათი გამოყენებით ნოდის არჩევას. ფაილში არის 12 არქიტექტურის 29 ნოდი,
რომლებიც `uint32_t` მასივის ჯამს ითვლიან.
თითო ნოდს საკუთარი `CODE` აქვს, ხოლო ყველა ნოდის მეტამონაცემები ინახება
**ერთ საერთო `METADATA` სექციაში, ფაილის ბოლოში**.

ამ განახლებაში შეტანილია მხოლოდ CPU მეტამონაცემების პროტოტიპი და მისი
შემოწმებისთვის საჭირო ჩამტვირთავი, გენერატორი და კოდის მაგალითები.
ქსელური და მიკროკონტროლერების მაგალითები ამ გამოქვეყნების ნაწილი არ არის.
ფორმატის ინგლისური აღწერა: [Architecture metadata](../docs/ARCHITECTURE_METADATA.md).

## გაშვება

Linux-ზე საჭიროა GCC, binutils, make და Python 3.10+.
სხვა არქიტექტურების ნამდვილი CODE ბინარები დართულია SHA-256 მანიფესტებით.

```sh
cd 12_shared_metadata
make test
./build/ueec-loader --list-technologies build/sum.ueec
./build/ueec-loader build/sum.ueec
```

`--list-technologies` თითო ნოდისთვის აჩვენებს `CODE` და `METADATA` სექციის
ინდექსებსაც. ნაგულისხმევ ფაილში ყველა სტრიქონს ექნება `METADATA=30`, ხოლო
`CODE` იქნება 1-დან 29-მდე. HEADER-ის ინდექსია 0.

```sh
./build/ueec-loader --technology avx2 build/sum.ueec
./build/ueec-loader --technology avx512f --fallback build/sum.ueec
./build/ueec-loader --groups
./build/ueec-loader --no-run build/sum.ueec
```

სხვა არქიტექტურაზე გამოიყენება მისი ტექნოლოგიის სახელი: მაგალითად `neon`,
`sve`, `lsx`, `lasx`, `altivec`, `rvv`, `vis` ან `vx`.
არჩევის წესი უცვლელია: თავსებად ნოდებს შორის ყველაზე მაღალი ავტორის მიერ
მინიჭებული პრიორიტეტი. ეს პროცესორის წარმადობის გაზომვა არ არის.

## საერთო METADATA-ს განლაგება

`ueec_metadata.h`-ში დამატებულია ახალი საცდელი დიზაინი:
`UEEC_MD_DESIGN_NODE_INDEXED = 1`. სექციის საცდელი ტიპი ისევ 13-ია.
UEEC v1-ის ძირითადი ჰედერი და ნოდის ჰედერი უცვლელია.

სექცია შეიცავს:

1. `ueec_md_hdr`: `uint16_t format`, `uint16_t design`.
2. ჩანაწერების რაოდენობას — format-ის მიხედვით 16, 32 ან 64 ბიტი.
3. ინდექსის ჩანაწერებს და ერთ დამატებით END ჩანაწერს.
4. ჩანაწერების მონაცემებს.

```c
typedef struct UEEC_PACKED {
    uint16_t node_index;
    uint16_t type;
    uint16_t offset;
} ueec_md_node_element16;

typedef struct UEEC_PACKED {
    uint16_t node_index;
    uint16_t type;
    uint32_t offset;
} ueec_md_node_element32;

typedef struct UEEC_PACKED {
    uint16_t node_index;
    uint16_t type;
    uint64_t offset;
} ueec_md_node_element64;
```

**`node_index` ყოველთვის 16-ბიტიანია**, count/offset-ის სიგანის მიუხედავად.
იგი არის ნოდის ნულიდან დაწყებული ინდექსი ფაილის ნოდების ცხრილში.
სტრუქტურების ზომებია 6, 8 და 12 ბაიტი; კომპილაციისას მოწმდება `_Static_assert`-ით.
ეს C ხედებია: ფაილში რიცხვები გამოკვეთილად იწერება/იკითხება გამოცხადებული endian-ით.
მოთხოვნების bitfield-ების პირდაპირი სერიალიზაცია არ ხდება.

`offset` ითვლება მონაცემების არეს დასაწყისიდან, ინდექსის ცხრილის შემდეგ.
ჩანაწერის ზომა მიიღება მომდევნო offset-ის სხვაობით. პირველის offset არის 0;
offset-ები მონოტონურია. ბოლო END ჩანაწერს აქვს `node_index=0`, `type=0`,
`offset=მონაცემების არეს სრული ზომა`; იგი ნოდი 0-ის მეტამონაცემი არ არის.

თითო ნოდის REQUIRED ჩანაწერს აქვს მისი არქიტექტურის ტიპი და `uint64_t` მოთხოვნები.
PRIORITY-ის ტიპია 2 და მნიშვნელობა `uint16_t`; მისი არყოფნისას პრიორიტეტია 0.
ერთ ნოდს რამდენიმე სხვადასხვა ტიპის ჩანაწერი ეკუთვნის.
ამ მაგალითში არის 58 ჩანაწერი: 29 REQUIRED და 29 PRIORITY, დამატებით END.

| REQUIRED ტიპი | ოჯახი |
| --- | --- |
| 1 | x86 / x86-64 |
| 0x100 | ARM32 |
| 0x101 | ARM64 |
| 0x102 | LoongArch64 |
| 0x103 | PowerPC32 / PowerPC64 |
| 0x105 | RISC-V32 / RISC-V64 |
| 0x107 | SPARC32 / SPARC64 |
| 0x10b | S390X |

ეს ინდექსები ჯერ მაგალითის საცდელი შეთანხმებაა და არა დასრულებული სტანდარტი.
ამ პროტოტიპში უცნობი ტიპი, განმეორებული REQUIRED/PRIORITY, არასწორი ზომა,
დაკარგული REQUIRED, არასწორი sentinel ან არარსებული ნოდის ინდექსი შეცდომაა.
უცნობი მოთხოვნის **ბიტი** ფორმატის შეცდომა არ არის: ნოდი შეუთავსებლად ითვლება.

## მიბმა და მეხსიერება

არსებული ნოდი–სექციის ცხრილი თითო ნოდს უკავშირებს მის CODE-სა და იმავე საერთო
METADATA-ს. მეტამონაცემის ინდექსის ჩანაწერი დამატებით ზუსტად ასახელებს ნოდს.
ჩამტვირთავი ყოველ ფიზიკურ METADATA სექციას ერთხელ აანალიზებს და **ყველა**
ჩანაწერს ამოწმებს, სხვა არქიტექტურისა და დაბალი პრიორიტეტის ნოდების ჩათვლით.
ჩანაწერმა მხოლოდ იმ ნოდზე შეიძლება მიუთითოს, რომელსაც ეს სექცია აქვს მიბმული.

METADATA ფაილის წაკითხვისას დროებით მეხსიერებაში ჩანს და საჭიროა არჩევისთვის.
არჩეული CODE ცალკე იტვირთება RW მეხსიერებაში, შემდეგ RX ხდება; მთელი ფაილის
დროებითი read-only mapping შესრულებამდე იხსნება. შედეგად შესრულებისთვის
ჩატვირთულია მხოლოდ ერთი CODE სექცია და იბეჭდება:

```text
EXECUTE resident_sections=1 metadata_resident=no
```

ფაილის ბოლოში მდებარეობა თავისთავად არ განსაზღვრავს რეზიდენტობას:
ამას ამ ჩამტვირთავის სექციის ტიპის დამუშავება განსაზღვრავს.
გენერატორი METADATA-ს ბოლოს წერს; ჩამტვირთავი მის მდებარეობას სექციების
აღწერიდან ადგენს და ფაილის ბოლოში ყოფნას არ ეყრდნობა.

ნოდის ამოღების ან ნოდების გადანომვრისას **METADATA-ს node_index-ებიც უნდა
გადაიწეროს**. ქსელური გადაცემისას ერთი ნოდის ახალ ფაილში ინდექსი იქნება 0;
სხვა ნოდების ჩანაწერები მას არ უნდა გაჰყვეს. ამ არქივში ქსელური ამომღები ჯერ არ არის.

## ძველ ფაილებთან თავსებადობა

ახალი ჩამტვირთავი კითხულობს design=0 ფორმატსაც: თითო ნოდის
ცალკე METADATA-ს, `type + offset` ჩანაწერებით. ძველი დიზაინის ერთ სექციას
რამდენიმე ნოდი ვერ გამოიყენებს, რადგან ჩანაწერებში node_index არ აქვს.
ძველი ჩამტვირთავი ახალი design=1 ფორმატის წამკითხველად არ ითვლება.

```sh
python3 generate.py --metadata-layout per-node --output build/legacy.ueec
./build/ueec-loader build/legacy.ueec
python3 generate.py --md-width 8 --endian big --output build/shared-be64.ueec
./build/ueec-loader build/shared-be64.ueec
```

იგივე CODE-ებით ნაგულისხმევი ფაილი შემცირდა **6049-დან 5719 ბაიტამდე**:
29 CODE + 29 METADATA-ის ნაცვლად არის 29 CODE + 1 METADATA.
CODE ბინარები და მოთხოვნების ბიტების ნომრები არ შეცვლილა.

## ყველა არქიტექტურის შემოწმება

```sh
set -o pipefail
make test-all 2>&1 | tee shared-metadata-test.log
printf 'Exit code: %s\n' "$?"
```

`make test-all` მოითხოვს ყველა 12 cross-კომპილატორსა და QEMU-ს;
დაკარგული სამიზნე ტესტს წყვეტს. `make test` მხოლოდ მიმდინარე არქიტექტურას აგებს.
ცალკეული არქიტექტურისთვის:

```sh
make loader ARCH=powerpc64
make generate
python3 test_dispatch.py --arch powerpc64 --qemu
```

აგების სკრიპტი მხარს უჭერს `CC_ARM32`, `CC_ARM64`, `CC_LOONGARCH64`,
`CC_POWERPC32`, `CC_POWERPC64`, `CC_RISCV32`, `CC_RISCV64`, `CC_SPARC32`,
`CC_SPARC64`, `CC_X86`, `CC_X86_64`, `CC_S390X` ცვლადებს.
RISC-V32-ისთვის ავტომატურად მოწმდება `/opt/riscv32/bin/riscv32-unknown-linux-gnu-gcc`.

PowerPC64-ის პროფილი ისევ POWER8-ია; POWER5+ მხარდაჭერა არ არის დადასტურებული.
GCC 15-ის ELFv1 descriptor-ის memory-operand შესწორება შენარჩუნებულია.
სხვა შეზღუდული CPU მოდელის ტესტამდე დამოუკიდებელი libc/ABI probe სრულდება.
თუ იგი ვერ ეშვება, JSON-შიც აღინიშნება მიუწვდომელი CPU-model შემოწმება;
შესაძლებლობების შემცირებული ნიღბით უარყოფისა და fallback-ის ტესტები მაინც სრულდება.
ჩამტვირთავის ავარია არასოდეს ითვლება წარმატებულ უარყოფით ტესტად.

შესრულების ტესტები ამოწმებს თითო ხელმისაწვდომ CODE-ს, 256 alignment/length
კომბინაციას, 32 guard-page შემთხვევას, NULL/zero-სა და uint32 overflow-ს.
დამატებით მოწმდება საერთო და ძველი დიზაინების LE/BE და 16/32/64 ვარიანტები,
დაზიანებული/დუბლირებული ნოდის ჩანაწერები და სხვა არქიტექტურის დაზიანებული MD.

ამ კონკრეტული გამოშვების რეალურად შესრულებული შემოწმებები იხილეთ `VALIDATION.md`-ში.

მეხსიერების საზღვრებისა და undefined behavior-ის დამატებითი შემოწმება:

```sh
make test-sanitize
```

თუ გარემოში LeakSanitizer-ს ptrace-ის გამო მუშაობა ეკრძალება, შეიძლება მხოლოდ
გაჟონვების შემოწმების გამორთვა: `ASAN_OPTIONS=detect_leaks=0 make test-sanitize`.
AddressSanitizer-ის საზღვრებისა და UBSan-ის შემოწმებები ამ დროს მაინც მოქმედებს.

## სამუშაოს წარმომავლობა

საერთო მეტამონაცემების ამ გამოშვების კოდი, ტესტები და დოკუმენტაცია მომზადდა
OpenAI-ის ასისტენტის მონაწილეობით. ქვემოთ დართული შემოწმებები შესრულებულია
რეალურად; ეს არ წარმოადგენს დამოუკიდებელი ადამიანის კოდის მიმოხილვას.
