# 15 — UEEC STM32: საერთო მეტამონაცემები და ვირტუალური გაშვება

სამი STM32 მოდელის LED blink პროგრამა ერთ UEEC ფაილში: **3 ნოდი, 3 CODE და 1 საერთო METADATA**. ჩამტვირთავი ვირტუალური მოწყობილობის პროფილის მიხედვით ავტომატურად არჩევს ნოდს, მხოლოდ მის კოდს წერს ვირტუალურ Flash-ში, ამოწმებს წაკითხულ მონაცემებს და უშვებს Cortex-M კოდს Renode-ში. LED-ის მდგომარეობის ცვლილებები GPIO მოდელიდან იკითხება; VCD სწორედ ამ მოვლენებიდან იქმნება.

| ვირტუალური მოდელი | ბირთვი | Flash | მოდელირებული RAM | საწყისი სიხშირე | LED |
|---|---|---:|---:|---:|---|
| STM32F103RB | Cortex-M3 | 128 KiB | 20 KiB | 8 MHz | PA5 |
| STM32F407VG | Cortex-M4 | 1 MiB | 128 KiB main SRAM | 16 MHz | PD12 |
| STM32F746NG | Cortex-M7 | 1 MiB | 320 KiB | 16 MHz | PI1 |

ეს სამი წინასწარ განსაზღვრული ვირტუალური დაფაა. `--mcu` ირჩევს მოწყობილობას და **არა UEEC ნოდს**. ჩამტვირთავის C ნაწილი კითხულობს Renode-დან მიღებულ CPUID-ს, Flash/RAM ზომებსა და SysTick-ის სიხშირეს; მოდელისა და დაფის პროფილთან ერთად ამოწმებს შესაბამისობას. CPUID მხოლოდ ბირთვს განასხვავებს და STM32-ის ზუსტ მოდელს დამოუკიდებლად ვერ ადგენს. მოდელის იდენტობა, შესაძლებლობების კატალოგი და LED-ის შეერთება პლატფორმის კონფიგურაციიდან მოდის.

## დაყენება და ტესტი

Linux-ზე საჭიროა Python 3.12 ან ახალი, C კომპილატორი და make. firmware-ს თავიდან ასაგებად საჭიროა ARM bare-metal GCC და binutils:

```sh
sudo apt update
sudo apt install build-essential python3 gcc-arm-none-eabi binutils-arm-none-eabi
cd 15_stm32_metadata
make test-all
```

პირველ გაშვებაზე, თუ `renode` PATH-ში არ არის, Linux x86-64-ზე ავტომატურად ჩამოიტვირთება ოფიციალური **Renode 1.17.0 portable** (~61 MiB), SHA-256-ის გადამოწმებით. ადმინისტრატორის უფლება არ სჭირდება. კომპილატორი firmware-ს ადგილობრივად ააგებს; Renode firmware-ს არ აგენერირებს. სხვა host არქიტექტურაზე დააყენეთ შესაბამისი Renode და მიუთითეთ მისი სრული გზა:

```sh
export RENODE=/absolute/path/to/renode
make test-all
```

ჩაშენებული `.bin` ფაილებით შემოწმება ARM კომპილატორის გარეშე:

```sh
make test
```

ორივე ტესტი სავალდებულოდ უშვებს სამივე ვირტუალურ მოდელს; გამოტოვებული სამიზნე წარმატებად არ ითვლება. შემოწმება მოიცავს რეალურ CPU/GPIO შესრულებას, არასწორ ვექტორებს, შეუთავსებელ მოდელებსა და შესაძლებლობებს, დაზიანებულ ინდექსებს, 256-ე ნოდის არჩევას და LED-ის პერიოდთან შეუსაბამობის აღმოჩენას.

## გამოყენება

```sh
# ვირტუალური სამიზნეების ჩამონათვალი
./build/ueec-stm32 --list-models

# ავტომატურად აირჩევა ამ მოწყობილობასთან თავსებადი ნოდი
./build/ueec-stm32 --mcu stm32f407vg build/blink.ueec

# ნოდების ნახვა მოწყობილობასთან თავსებადობის ჩვენებით
./build/ueec-stm32 --mcu stm32f746ng --list-nodes build/blink.ueec

# არჩევა Flash-ში ჩაწერისა და შესრულების გარეშე
./build/ueec-stm32 --mcu stm32f103rb --no-run build/blink.ueec

# რეალური GPIO მოვლენების VCD, JSON ანგარიში და Renode-ის სრული ლოგი
./build/ueec-stm32 --mcu stm32f407vg \
  --vcd build/led.vcd --report build/led.json --log build/led.log \
  build/blink.ueec
```

VCD ფაილზე არსებული მონაცემები არ გადაიწერება; აირჩიეთ ახალი სახელი ან წაშალეთ წინა შედეგი. LED-ის ნახევარპერიოდია 100 ms. ნაგულისხმევად მოწმდება რვა ცვლილება და მათი დროები, 2%-იანი დასაშვები ცდომილებით. VCD-ის ნახვა შეიძლება GTKWave-ში.

## მეტამონაცემები

საერთო METADATA სექცია ფაილის ბოლოშია და Flash-ში არ იწერება. მისი დიზაინი იგივეა, რაც მე-12 და მე-13 მაგალითებში: `format`, `design=1`, შესაბამისი სიგანის `count`, შემდეგ ინდექსი და მონაცემები.

```c
typedef struct UEEC_PACKED {
    uint16_t node_index;  /* ყოველთვის 16 ბიტი */
    uint16_t type;
    uint16_t offset;      /* format-ის მიხედვით: uint16_t/uint32_t/uint64_t */
} ueec_md_node_element16;
```

| ტიპი | ზომა | შინაარსი |
|---|---:|---|
| `0x210` STM32_TARGET | 24 B | მოდელი, CPUID part, Flash/RAM მისამართები და ზომები, სიხშირე |
| `0x211` STM32_REQUIRED | 8 B | საჭირო შესაძლებლობების ერთიანი ბიტური სივრცე |
| `0x212` STM32_BLINK | 8 B | GPIO ბაზა, პორტი, პინი, ნახევარპერიოდი |
| `2` PRIORITY | 2 B | თავსებად ნოდებს შორის არჩევის პრიორიტეტი |

შესაძლებლობების ბიტებია: Thumb-2, DSP, FPUv4 SP, FPUv5 SP, I-cache, D-cache. ამ კონკრეტული firmware-ს მოთხოვნა მხოლოდ Thumb-2-ია; იგი `soft-float` რეჟიმშია აგებული. DSP/FPU/cache-ის არსებობა პროფილის ინფორმაციაა და ამ ტესტით მათი შესრულება არ მოწმდება.

სტრუქტურები იხილეთ `ueec_stm32_metadata.h`-ში. C bitfield არის მოსახერხებელი წარმოდგენა; დისკზე მონაცემები იწერება აშკარა ბიტური ნიღბებით და ფაილის ბაიტური რიგით. `packed` C bitfield-ის პორტატულ ბინარულ განლაგებას არ უზრუნველყოფს. ინდექსის ბოლო ჩანაწერია `node_index=0, type=0, offset=data_size`; offset იზომება მონაცემების არეალის დასაწყისიდან. CODE-ის ვექტორები და ARM ბრძანებები ყოველთვის little-endian რჩება, outer UEEC კონტეინერის ბაიტური რიგის მიუხედავად.

ეს STM32 ტიპების ნომრები ამ მაგალითის პროტოტიპული განაწილებაა. არსებულ UEEC რეესტრთან საბოლოო გაერთიანება ცალკე დასამტკიცებელია.

## რეალიზაცია და საზღვრები

- UEEC-ის პარსინგი, მეტამონაცემების შემოწმება, ნოდის არჩევა და CODE-ის გამოყოფა **C-ზეა** (`loader.c`). Python მართავს build-ს, Renode-ის პროცესს, ანგარიშებსა და ტესტებს. ეს Python-ზე დაწერილი CPU ემულატორი არ არის.
- firmware-ს აქვს საკუთარი ვექტორების ცხრილი, reset/startup, `.data`/`.bss` ინიციალიზაცია და SysTick-ის დამმუშავებელი. იგი GPIO-ს BSRR რეგისტრს წერს; დაყოვნებისას WFI გამოიყენება. HAL, OS და newlib საჭირო არ არის.
- Renode ასრულებს Cortex-M ბრძანებებს, NVIC/SysTick გამონაკლისებსა და GPIO მოდელს. ეს მინიმალური პლატფორმებია, სრული STM32 ჩიპის ან ელექტრონული დაფის ზუსტი მოდელები არ არის.
- F103-ის RCC enable რეგისტრი RAM-ის მსგავსი ჩრდილოვანი ბლოკითაა წარმოდგენილი; სრული PLL/clock gating არ მოწმდება. F4/F7 იყენებს Renode-ის STM32F4 RCC მოდელს, მაგრამ სრული საათების ხის სიზუსტე არც აქაა ნაჩვენები.
- F407-ის რეალური 192 KiB SRAM-დან მაგალითი მხოლოდ 128 KiB main SRAM-ს იყენებს; 64 KiB CCM გამოტოვებულია. F746-ის 320 KiB RAM ერთ ბლოკადაა წარმოდგენილი; TCM/cache-ის განსხვავებული დროები არ მოდელირდება.
- ვირტუალურ Flash-ში ჩაიწერება მხოლოდ არჩეული CODE და იკითხება გადამოწმებისთვის. ეს Flash კონტროლერის პროგრამირების ალგორითმის ან ST-Link-ის ტესტი არ არის. ფიზიკურ STM32-ზე ეს მაგალითი ჯერ არ შემოწმებულა.

## შემოწმების მასალები

`validation/` შეიცავს ტესტების ლოგებს, ხელსაწყოების ვერსიებსა და გაშვების ანგარიშს. `examples/`-შია UEEC ფაილი და სამივე მოდელის GPIO JSON/VCD კვალი. ახალი შედეგები იქმნება `build/results/`-ში.

```sh
make test-sanitize  # C პარსერი/შემრჩევი ASan + UBSan-ით, იგივე ტესტები
```

Renode-ის გარე runtime სანიტაიზერით არ იკომპილირება. შემოწმების ზუსტი ფარგლები აღწერილია `VALIDATION.md`-ში.
